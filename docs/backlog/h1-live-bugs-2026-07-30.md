## 1. One HTML allowlist, copied four times (FB-24, FB-21)

**FB-24 is the most damaging item in the batch and the cheapest to fix.**

The question-body allowlist is `b, i, u, ul, ol, li, sup, sub, img`. `br`, `p` and `div` are **not on
it** — and `<div>`/`<br>` is exactly what a `contentEditable` emits when you press Enter. bluemonday
strips a non-allowlisted element but keeps its text, so `<div>A</div><div>B</div>` is persisted as
`AB`. The admin types paragraphs, saves, and the breaks are gone. The code comments already know:

> *"Callers sanitize `q.Body` via `sanitizeQuestionBody` before calling here, which strips
> non-allowlisted tags (e.g. `<br>`) with no text content down to `""`."*
> — [`exam.go:172-174`](../../backend/internal/service/exam.go)

A body of nothing but line breaks therefore sanitizes to `""` and is rejected as *"body cannot be
empty"*.

**The same list is written out four separate times**, and they are currently identical:

| # | File | Role | Breaks if only this one changes |
|---|---|---|---|
| 1 | [`exam.go:61`](../../backend/internal/service/exam.go) (bluemonday) | write-time, **destructive** | nothing — but the tag still dies at 3 and 4 |
| 2 | [`RichTextEditor.tsx:42`](../../web/components/admin/RichTextEditor.tsx) | paste into the editor | pasted markup silently differs from typed |
| 3 | [`RichContent.tsx:17`](../../web/components/admin/RichContent.tsx) | **admin** preview render | preview lies about what students see |
| 4 | [`sessions/[id]/page.tsx:735`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx) | **student** exam render | admin sees it, student does not |

Copy 1 is the destructive one — it changes what is stored. Copies 3 and 4 only change what is drawn.
Any tag added to one and not the others produces a surface that disagrees with itself, and **no test in
the tree compares the four lists**. That is the FB-21 (table) problem too: `table, thead, tbody, tr,
th, td` must land in all four plus a toolbar affordance, or a pasted table survives the round-trip and
then vanishes for the student.

**Fix, in order:**

1. Add `br` and `p` to all four lists in one commit. Add a test that asserts the four are equal — the
   duplication is the actual defect and it will bite again on FB-21.
2. Re-check the empty-body rule: `<br>` alone must still be rejected once `br` is allowed, or a blank
   question becomes saveable.
3. FB-21 (table) is a separate, larger change: allowlists + toolbar + a decision on whether a pasted
   Word/Excel table is in scope. Do it after FB-24 ships, not in the same commit.

**FB-24 is a data-loss bug on every save since the sanitizer landed.** Questions already authored have
lost their breaks in the database; the text is intact but the paragraphing is not recoverable.

## 2. The toolbar runs `execCommand` after losing the caret (FB-22, FB-23)

[`RichTextEditor.tsx`](../../web/components/admin/RichTextEditor.tsx) is a `contentEditable` driven by
`document.execCommand`, and every toolbar control is a real focusable `<button>`:

```tsx
function exec(cmd: string, arg?: string) {
  document.execCommand(cmd, false, arg);   // runs first…
  if (ref.current) ref.current.focus();    // …focus restored after. Too late.
}
```

`execCommand` acts on the current selection. Clicking a `<button>` moves focus out of the editable
first, and nothing saves or restores the Range across that click — the focus call happens *after* the
command it was supposed to enable. There is no `onMouseDown` `preventDefault()` anywhere in the file.

- **FB-22 (bullets/numbering)** — `insertUnorderedList` / `insertOrderedList` need a live caret inside
  the editable. With the caret gone they no-op, which is exactly "tidak bisa di klik".
- **FB-23 (image)** — worse: `fileInputRef.current?.click()` opens the OS file dialog, focus leaves
  entirely, and the `exec("insertHTML", "<img …>")` fires *after* the upload resolves, by which point
  there is certainly no selection in the editable. **The file uploads successfully and the `<img>` is
  never inserted** — no error is shown, because `sync()` reports the unchanged HTML.

**FB-23 has a second candidate cause; check both.** The inserted markup carries
`style="max-width:60%;border-radius:8px;margin:6px 0"`, and the backend style allowlist is
`color, background-color, text-align, font-weight, font-style, text-decoration`
([`exam.go:68`](../../backend/internal/service/exam.go)) — so those declarations are stripped on save.
That does not remove the image, but it does mean a *saved* image renders unsized. Rule the read path
out too: `fileUrl(key)` resolves to `<api>/files/<key>` and `question/` **is** on the read-proxy
allowlist ([`student.go:365-369`](../../backend/internal/service/student.go)), so the proxy is not the
problem — but confirm with a browser network tab rather than on my reading.

**These are the two items in the batch I would reproduce in a browser before touching**, because the
fix differs: preserving the selection (a small, safe change) vs. abandoning `execCommand` for a real
editor. `document.execCommand` is deprecated; if bullets, image insert *and* FB-21 tables all need it,
replacing the editor becomes the cheaper path. Decide that deliberately — it is a bigger change than
the three items suggest, and it touches the same file as FB-24.

## 3. FB-25 — the editor never writes the `{{N}}` token it shows you

The client's quoted message is real, modulo their transcription. The literal string is
[`exam.go:141`](../../backend/internal/service/exam.go):

```go
return fmt.Errorf("%w: multi_blank requires at least one {{N}} token", ErrValidation)
```

Tokens are `{{1}}`, `{{2}}` — double braces — and must form a contiguous `1..N` set with one blank per
token ([`extractTokensFromStem`, `validateTokenSequence`](../../backend/internal/service/exam.go)).

The authoring UI gets this half right and then strands the admin. `BlankEditor`
([`QuestionEditor.tsx:56-100`](../../web/components/admin/QuestionEditor.tsx)) renders the label
`` `{{${blank.index}}}` `` beside each blank row — so the admin *sees* `{{1}}` and reasonably assumes
adding a blank inserts it. It does not: **nothing writes the token into the body.** And the client-side
validator does not mirror the backend rule —
[`QuestionEditor.tsx:332-341`](../../web/components/admin/QuestionEditor.tsx) checks only that blanks
exist and have answers:

```ts
if (format === "multi_blank") {
  if (blanks.length === 0) return { ok: false, key: "tests_validation_blanks_required" };
  for (const blank of blanks) { if (!blank.correct_answer.trim()) … }
}
```

So the form submits happily and the server rejects it with a message written for a developer.

**Fix:** an **Insert blank** action that writes `{{N}}` at the caret *and* appends the matching blank
row, keeping the two in lockstep. Mirror the token/blank-count check client-side with a message that
names what to do. Note the caret problem from [§2](#2-the-toolbar-runs-execcommand-after-losing-the-caret-fb-22-fb-23)
applies to this insert too — **fix §2 first or the new button will fail the same way.**

## 4. FB-26 — the second attempt is impossible, and that is the specification

> **Corrected after checking the PRD.** An earlier version of this section called the hardcoded guard
> "the bug". It is not — **it is the spec**, and the real defect is one layer up. See
> [§13](#13-conflicts-with-the-prd--trd) for the full conflict.

**PRD FR-COMP-02 (Must):** *"Every exam is single-attempt: `ExamRegistration.attempts_used` is a stored
counter, incremented atomically at session start (`WHERE attempts_used = 0` guard); a second start
returns 409. `Exam.max_attempts` is stored but **not consulted** — multi-attempt/unlimited support
**deferred**; remedial = a separate exam. (Superseded 2026-07-07 …)"* The TRD says the same thing twice,
in comments on both columns.

**So the engine is correct and the admin form is the liar.** FR-EXAM-09 lists `max_attempts` as an
editable field on the exam form, so the client set it to 2, was given no warning, and reasonably
expected two attempts. Everything below stays true as a description of the code — read it as *what
implementing multi-attempt would take*, not as a defect list.

`exam.max_attempts` is stored, validated (*"max_attempts cannot be negative"*,
[`exam.go:649`](../../backend/internal/service/exam.go)) and **never read at start-session time**. The
guard is a hardcoded literal, [`exam.go:1349-1366`](../../backend/internal/repository/exam.go):

```sql
UPDATE exam_registration
SET attempts_used = attempts_used + 1, status = 'in_progress',
    checked_in_at = COALESCE(checked_in_at, now())
WHERE id = $1 AND attempts_used = 0      -- ← ignores max_attempts entirely
```

`RowsAffected() == 0` → `ErrNoAttemptsLeft`. So the second start always fails, whatever the admin
configured. The comment calls the predicate *"the atomic 1-attempt guard"* — it is doing precisely
what it says, which is the bug: the intent was concurrency safety, and the attempt ceiling got baked in
as a constant on the way.

The `INSERT` in the same function is wrong for the same reason:

```sql
INSERT INTO exam_session (…, attempt_number, …) VALUES ($1, $2, $3, 1, now(), 'in_progress')
```

`attempt_number` is the literal `1`, so even with the predicate fixed every attempt would claim to be
the first.

**The cheap fix is not the code — it is the form.** Two options, and the client picks:

| Option | Cost | Consequence |
|---|---|---|
| **A. Remove `max_attempts` from the admin form** and state "single attempt" | hours | Honest immediately. Matches FR-COMP-02 and the 2026-07-07 deferral. The client loses a capability they never actually had. |
| **B. Implement multi-attempt** | days, + schema semantics | **Reverses a documented deferral — a scope change needing sign-off**, exactly like NF-1. Recorded in [prd-trd-drift](prd-trd-drift.md) §1. |

**Ship A now regardless of which they choose** — leaving a field that silently does nothing is the
actual harm, and A does not block B.

**If B is chosen — three parts, all in the one transaction:**

1. `WHERE id = $1 AND attempts_used < $2`, passing `exam.max_attempts`. **Keep it in the predicate** —
   moving the check to the service layer reintroduces the race the comment is guarding against.
2. `attempt_number` = `attempts_used + 1` from the returning row, not a literal.
3. Decide what `max_attempts = 0` means (unlimited, or none) and write it down — the validator only
   rejects negatives today.

Then check the *frontend* gate as well: `computeCardState`
([`(student)/exam/page.tsx:70-71`](../../web/app/(student)/exam/page.tsx)) maps
`status === "in_progress"` to a detail link, not a Start action — and §5 explains why the status never
leaves `in_progress`. **A registration stuck at `in_progress` blocks the retry in the UI even after
the SQL is fixed.** Both layers, one branch — fixing the repository alone and calling FB-26 done is the
exact shape of a fix that passes its own tests and stays broken on screen.

## 5. FB-27 — a submitted result is unreachable after logout

Not a data-loss bug: the score is on `exam_session` and stays there. There is simply **no route back
to it**, and the code says so in a comment written before the demo
([`(student)/exam/page.tsx:64-68`](../../web/app/(student)/exam/page.tsx)):

> *"`submitted` isn't derivable here — `exam_registration.status` never advances past `in_progress` on
> submit (score lives on `exam_session`, which this list endpoint doesn't join) — see registration
> detail page for the same gap. `in_progress` renders as a link to the detail page instead of a
> fabricated 'view result' action."*

Two facts follow, and together they are the whole bug:

1. **`exam_registration.status` never advances to `submitted`.** So no surface can tell a finished exam
   from one in progress.
2. **There is no list-sessions endpoint.** The student routes are `GET /exam/sessions/:id`,
   `.../result`, `.../leaderboard` ([`routes.go:126-140`](../../backend/internal/server/routes.go)) —
   all keyed by a session id the student only ever held in memory, on the redirect after submit. Log
   out and the id is gone; the result page still exists and is still permitted, and nothing links to it.

**Fix:** advance `exam_registration.status` to `submitted` on submit (this also unblocks FB-26's UI
gate), join the score into the registrations list, and give the card a **Lihat hasil** action. Whether
a `GET /exam/sessions` list is also needed depends on whether one registration can now have several
sessions — which FB-26 makes true. **Do FB-26 and FB-27 in one branch:** they share the status
transition and the same list endpoint, and fixing either alone leaves a half-working retry.

This is *not* FB-2. FB-2 is the **admin** results tab. This is the student's own history, and no item
in the 2026-07-29 batch covered it.

## 6. FB-32 — question audio renders only in a sectioned listening test

The admin can set an audio URL on any question — `QuestionEditor` exposes `tests_field_audio_url` for
every format ([`QuestionEditor.tsx:610-613`](../../web/components/admin/QuestionEditor.tsx)) with no
warning attached. The player is behind a two-part gate
([`sessions/[id]/page.tsx:532`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx)):

```tsx
{isSectioned && activeTest?.section_type === "listening" && currentQ?.audio_url && (
  <QuestionAudioPlayer audioUrl={currentQ.audio_url} … />
)}
```

`isSectioned` is true only for `mode = utbk | ielts`
([`isSectionedMode`, `exam.go:54`](../../backend/internal/service/exam.go)). So audio set on a question
is **silently discarded at render** in either of two very ordinary cases:

- the exam is `mode = standard` — the default; or
- the exam is sectioned but the test has no `section_type = 'listening'` (it is nullable).

The section-level player at line 523 has the identical gate. Nothing in the authoring UI says the field
is conditional, and nothing warns on save.

**A listening question with no audio is unanswerable**, which is why this is P0 rather than a missing
feature.

**The PRD contradicts itself here, so the fix needs a decision — see [§13](#13-conflicts-with-the-prd--trd).**
FR-COMP-19a specifies **section-level** audio only (*"one audio file per exam section shared across all
questions in that section"*), and FR-EXAM-05 puts `audio_url` / `audio_play_limit` on **Test**.
FR-EXAM-01 lists question attachments as **image only**. But the PRD's own prose overview promises
*"Image and audio attachments **per question**"*. `question.audio_url` shipped in migration 0028 and
reached neither document — the same undocumented-field class as `multi_blank`.

So the render gate matches the **specified** model; the authoring field is what has no spec.

**Fix — whichever the client confirms, both ends must agree:**

- **Per-question audio is in scope** (what the prose says, and what they evidently expected): render the
  player whenever `audio_url` is present, independent of `section_type`. Then decide what
  `audio_play_limit` means for a single question, since it was written for a shared section file.
- **Section-level only** (what the FR table says): the authoring UI must **remove or disable** the
  per-question audio field. Do not leave it visible and inert — that is FB-26's failure again.

Either way, add the field to the TRD ERD; [prd-trd-drift](prd-trd-drift.md) §2 item 3 already notes
`Question.audio_url` is missing from it.

## 7. FB-33 — up to 30 seconds of answers are lost, silently (widens FB-20)

**This contradicts a claim in [E3](e3-exam-delivery-results.md), which must be corrected.** E3 §4 says
answers *"are persisted server-side on every change"* and that only the position is lost. They are not.
[`sessions/[id]/page.tsx:250-263`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx):

```tsx
// Periodic save every 30s
const id = setInterval(() => {
  if (submittingRef.current) return;
  const arr = buildSavePayload();
  if (arr.length > 0) saveAnswers.mutate(arr);   // fire-and-forget
}, 30000);
```

Three separate defects in five lines:

1. **A 30-second window.** Answers between ticks exist only in React state. A disconnect, a reload or a
   kicked session drops them.
2. **`.mutate`, not `.mutateAsync`, with no `onError`.** A save that fails while the network is down
   fails *silently*. No retry, no queue, no backoff — the next attempt is another 30 s away, and if the
   connection is still down that one is lost too.
3. **No unsaved indicator anywhere.** The student has no way to know their last five answers are only
   in the tab. This is what makes it a trust bug rather than a latency bug.

On reconnect the page hydrates from `session.answers`
([lines 124-133](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx)) — so the student is shown
exactly what reached the server, with no indication that anything is missing. `currentQIndex` resets to
`0` (that part is FB-20, correctly described).

**Fix:** save on change (debounced ~1–2 s), retry with backoff on failure, keep a durable local queue
so a save survives a reload, and show a saved/unsaved state. **Fold this into FB-20** — the position
belongs in the same write, and FB-20's acceptance criterion ("same question, same answers") is
untestable until the answer path is trustworthy. Widen FB-20's scope in E3 rather than tracking two
items over one code path.

## 8. FB-31 — alt+tab is detected, counted, and then nothing happens

**This is FR-COMP-13 (Must) working exactly as written**, and the FR is fully satisfied:

> *"Proctoring events **detected, warned to student, and logged with timestamp**. Shipped vocabulary:
> `fullscreen_exit`, `tab_switch` (fires on any visibility change, which covers new-tab/new-window
> focus loss), `copy_attempt`."*

Detect, warn, log — three things, all three shipped. **The spec names no consequence**, so there is no
defect here: the client is asking for a *new* behaviour, not a repair. FR-COMP-12 likewise specifies
only *"opens fullscreen; re-prompted on exit"*, which is the overlay they are seeing.

Behaviour confirmed, and the client's reading of it is correct.
[`sessions/[id]/page.tsx:265-291`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx) listens
for `visibilitychange`, `fullscreenchange` and `copy`, logs `tab_switch` / `fullscreen_exit` /
`copy_attempt` via `POST /exam/sessions/:id/violations`, bumps `violationCountRef`, and shows an
overlay. `violationCountRef` is then used in exactly one place — **rendering the number**
([line 702](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx)). There is no threshold, no
auto-submit, no server-side aggregate action. `LogViolation`
([`exam_session.go:787-820`](../../backend/internal/service/exam_session.go)) validates the type and
writes a row.

So: switching away is *possible* (a browser cannot prevent it — no web API blocks alt+tab; only a
kiosk/lockdown browser or a native app can), it is *recorded*, and it *costs nothing*.

**This needs a product decision, not a fix.** The realistic options:

| Option | Cost | Note |
|---|---|---|
| Auto-submit after N violations | small — the counter exists | Harsh; one accidental notification ends an exam. Needs an admin-settable N. |
| Surface the count to the proctor live | small | `GetRecentViolations` already feeds the monitoring view. Human judgement, no false-positive risk. |
| Make it visible on the result / to the admin | small | Turns it into evidence rather than enforcement. |
| Actually prevent it | **not possible in a browser** | Requires a lockdown browser or native app. Out of scope; say so plainly to the client. |

Recommend the proctor-visible route plus an admin-configurable auto-submit threshold defaulting to
off. **Ask the client which consequence they want** before building any of it — this is the one item in
the batch where the code is behaving as designed and the design is what is in question.

## 9. FB-28 — no default certificate (needs repro)

**I could not locate a root cause, and the code argues against the report.** Defaults exist and are
deliberate: three backgrounds are `go:embed`-ed
([`certificate.go:42-56`](../../backend/internal/service/certificate.go)), `resolveCertificateLayout`
falls back to `defaultLayout(tmpl)`, and the comment states the intent — *"an exam never opens to an
empty canvas (FR-29)"*. `exam.certificate_design` carries a `template` key defaulting to `classic`
(migrations [0016](../../backend/db/migrations/0016_exam_certificate.up.sql),
[0042](../../backend/db/migrations/0042_certificate_design.up.sql)).

Three candidates, in the order I would check them:

1. **The render never runs.** A certificate needs `sess.Status == "submitted"` plus the result gate
   ([`resolveCertificateURL:334`](../../backend/internal/service/certificate.go)), and both return
   `nil, nil` — *no error* — when unmet. A student who cannot reach their result at all (**FB-27**)
   never reaches the certificate either. **Check FB-27 first; this may not be a separate bug.**
2. **Gotenberg fails at render time.** The sidecar is declared in
   [`deployments/app-production-app.yaml:48`](../../deployments/app-production-app.yaml), so it is not
   missing from the compose file — but **an end-to-end render has never been verified in any
   environment**. That is already logged as E1 verification debt and it is now blocking a client
   report. Do that render.
3. **The admin studio preview is what is blank**, not the student's certificate — a different code path

## 10. FB-34 — the region seed is pre-2022 (34 provinces, not 38)

Exact and fixable. [`0029_seed_province_city_district.up.sql`](../../backend/db/migrations/0029_seed_province_city_district.up.sql)
is stamped:

```sql
-- Auto-generated from emsifa/api-wilayah-indonesia static data
-- Generated at: 2026-07-18T00:04:40+07:00
-- 34 provinces
```

**34 provinces, 514 cities, 7215 districts.** That is Permendagri 72/2019 vintage. Indonesia has had
**38 provinces since 2022** — the file contains only `'91' PAPUA BARAT` and `'94' PAPUA`, so **Papua
Selatan, Papua Tengah, Papua Pegunungan and Papua Barat Daya are absent entirely**, along with the
kabupaten reassigned or created in that reorganisation. The generation date is recent; the *upstream
dataset* is not. A participant from those regions cannot complete their profile, which is exactly
"belum lengkap".

**Do not truncate and reload.** `orders` FKs into all three tables
([`0033_shipping_ongkir.up.sql:5-9`](../../backend/db/migrations/0033_shipping_ongkir.up.sql)):

```sql
ALTER TABLE orders ADD COLUMN province_id TEXT REFERENCES province(id);
ALTER TABLE orders ADD COLUMN city_id     TEXT REFERENCES city(id);
ALTER TABLE orders ADD COLUMN district_id TEXT REFERENCES district(id);
```

A reload that reissues ids breaks every historical order's shipping address. Write it as an **additive**
migration against a current Kemendagri/BPS code list: insert the new provinces and kabupaten, re-parent
moved rows by id, and leave existing ids alone. Ids in this dataset are official region codes, so a
moved kabupaten keeps its code and only its `province_id` changes — that is the property that makes an
additive migration safe. **Verify that assumption against the source list before writing the migration**;
if any code was reissued, the safe move is to keep the old row and add the new one.

Check whether Biteship's own region list is the shipping source of truth before syncing — if it is,
these tables serve the *profile* only and the blast radius is smaller than the FK suggests.
