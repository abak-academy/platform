## 1. One HTML allowlist, copied four times (FB-24, FB-21)

**FB-24 is the most damaging item in the batch and the cheapest to fix.**

The question-body allowlist is `b, i, u, ul, ol, li, sup, sub, img`. `br`, `p` and `div` are **not on
it** — and `<div>`/`<br>` is exactly what a `contentEditable` emits when you press Enter. bluemonday
strips a non-allowlisted element but keeps its text, so `<div>A</div><div>B</div>` is persisted as
`AB`. The admin types paragraphs, saves, and the breaks are gone. The code comments already know:

> *"Callers sanitize `q.Body` via `sanitizeQuestionBody` before calling here, which strips
> non-allowlisted tags (e.g. `<br>`) with no text content down to `""`."*
> — [`exam.go:172-174`](../../backend/internal/service/exam.go)

A body of nothing but line breaks therefore sanitizes to `""` and is rejected as *"body cannot be
empty"*.

**The same list is written out four separate times**, and they are currently identical:

| # | File | Role | Breaks if only this one changes |
|---|---|---|---|
| 1 | [`exam.go:61`](../../backend/internal/service/exam.go) (bluemonday) | write-time, **destructive** | nothing — but the tag still dies at 3 and 4 |
| 2 | [`RichTextEditor.tsx:42`](../../web/components/admin/RichTextEditor.tsx) | paste into the editor | pasted markup silently differs from typed |
| 3 | [`RichContent.tsx:17`](../../web/components/admin/RichContent.tsx) | **admin** preview render | preview lies about what students see |
| 4 | [`sessions/[id]/page.tsx:735`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx) | **student** exam render | admin sees it, student does not |

Copy 1 is the destructive one — it changes what is stored. Copies 3 and 4 only change what is drawn.
Any tag added to one and not the others produces a surface that disagrees with itself, and **no test in
the tree compares the four lists.**

> **The allowlist is a security boundary, and its narrowness was deliberate** — stored XSS was closed on
> this surface during the PR #34 review. `br` and `p` are safe to add (`br` is void; `p` carries no
> attributes under `AllowElements`), but widen it by *naming elements*, never by relaxing the policy.

**Fix, in order:**

1. Add `br` and `p` to all four lists **in one commit**. Add a test asserting the four are equal — the
   duplication is the actual defect and it will bite again on FB-21.
2. Re-check the empty-body rule: `<br>` alone must still be rejected once `br` is allowed, or a blank
   question becomes saveable.
3. **FB-21 (table) is a separate, larger change** — `table, thead, tbody, tr, th, td` in all four lists,
   plus a toolbar affordance, plus a decision on pasted Word/Excel tables. After FB-24 ships, not in the
   same commit.

**FB-24 is a data-loss bug on every save since the sanitizer landed.** Questions already authored have
lost their breaks in the database; the text is intact but the paragraphing is not recoverable.

**No FR covers any of this.** The PRD specifies KaTeX math and image attachments and says *nothing*
about text formatting, bullets, line breaks or tables — so these are defects against reasonable
expectation, not against a spec ([prd-trd-drift](prd-trd-drift.md) §2 item 12). FB-24 is a P0 on its own
merit regardless.

## 2. The toolbar runs `execCommand` after losing the caret (FB-22, FB-23)

[`RichTextEditor.tsx`](../../web/components/admin/RichTextEditor.tsx) is a `contentEditable` driven by
`document.execCommand`, and every toolbar control is a real focusable `<button>`:

```tsx
function exec(cmd: string, arg?: string) {
  document.execCommand(cmd, false, arg);   // runs first…
  if (ref.current) ref.current.focus();    // …focus restored after. Too late.
}
```

`execCommand` acts on the current selection. Clicking a `<button>` moves focus out of the editable
first, and nothing saves or restores the Range across that click — the focus call happens *after* the
command it was supposed to enable. There is no `onMouseDown` `preventDefault()` anywhere in the file.

- **FB-22 (bullets/numbering)** — `insertUnorderedList` / `insertOrderedList` need a live caret inside
  the editable. With the caret gone they no-op, which is exactly "tidak bisa di klik".
- **FB-23 (image)** — worse: `fileInputRef.current?.click()` opens the OS file dialog, focus leaves
  entirely, and `exec("insertHTML", "<img …>")` fires *after* the upload resolves, by which point there
  is certainly no selection in the editable. **The file uploads successfully and the `<img>` is never
  inserted** — no error is shown, because `sync()` reports the unchanged HTML.

**FB-23 has a second candidate cause; check both.** The inserted markup carries
`style="max-width:60%;border-radius:8px;margin:6px 0"`, and the backend style allowlist is
`color, background-color, text-align, font-weight, font-style, text-decoration`
([`exam.go:68`](../../backend/internal/service/exam.go)) — so those declarations are stripped on save.
That does not remove the image, but a *saved* image renders unsized. The read path is ruled out:
`fileUrl(key)` resolves to `<api>/files/<key>` and `question/` **is** on the read-proxy allowlist
([`student.go:365-369`](../../backend/internal/service/student.go)) — confirm with a network tab rather
than on my reading.

**Reproduce these two in a browser before touching them**, because the fix differs: preserving the
selection (small, safe) vs. abandoning `execCommand` for a real editor. `document.execCommand` is
deprecated; if bullets, image insert *and* FB-21 tables all need it, replacing the editor becomes the
cheaper path. Decide that deliberately — it is a bigger change than the three items suggest, and it
touches the same file as FB-24.

## 3. FB-25 — the editor never writes the `{{N}}` token it shows you

The client's quoted message is real, modulo their transcription. The literal string is
[`exam.go:141`](../../backend/internal/service/exam.go):

```go
return fmt.Errorf("%w: multi_blank requires at least one {{N}} token", ErrValidation)
```

Tokens are `{{1}}`, `{{2}}` — **double** braces — and must form a contiguous `1..N` set with one blank
per token ([`extractTokensFromStem`, `validateTokenSequence`](../../backend/internal/service/exam.go)).

The authoring UI gets this half right and then strands the admin. `BlankEditor`
([`QuestionEditor.tsx:56-100`](../../web/components/admin/QuestionEditor.tsx)) renders the label
`` `{{${blank.index}}}` `` beside each blank row — so the admin *sees* `{{1}}` and reasonably assumes
adding a blank inserts it. It does not: **nothing writes the token into the body.** And the client-side
validator does not mirror the backend rule
([`QuestionEditor.tsx:332-341`](../../web/components/admin/QuestionEditor.tsx)):

```ts
if (format === "multi_blank") {
  if (blanks.length === 0) return { ok: false, key: "tests_validation_blanks_required" };
  for (const blank of blanks) { if (!blank.correct_answer.trim()) … }
}
```

So the form submits happily and the server rejects it with a message written for a developer.

**Fix:** an **Insert blank** action that writes `{{N}}` at the caret *and* appends the matching blank
row, keeping the two in lockstep. Mirror the token/blank-count check client-side with a message that
names what to do. **The caret problem from [§2](#2-the-toolbar-runs-execcommand-after-losing-the-caret-fb-22-fb-23)
applies to this insert too — fix §2 first or the new button fails the same way.**

## 4. FB-27 — a submitted result is unreachable after logout

Not a data-loss bug: the score is on `exam_session` and stays there. There is simply **no route back to
it**, and the code says so in a comment written before the demo
([`(student)/exam/page.tsx:64-68`](../../web/app/(student)/exam/page.tsx)):

> *"`submitted` isn't derivable here — `exam_registration.status` never advances past `in_progress` on
> submit (score lives on `exam_session`, which this list endpoint doesn't join) — see registration
> detail page for the same gap. `in_progress` renders as a link to the detail page instead of a
> fabricated 'view result' action."*

Two facts follow, and together they are the whole bug:

1. **`exam_registration.status` never advances to `submitted`.** No surface can tell a finished exam
   from one in progress.
2. **There is no list-sessions endpoint.** The student routes are `GET /exam/sessions/:id`,
   `.../result`, `.../leaderboard` ([`routes.go:126-140`](../../backend/internal/server/routes.go)) —
   all keyed by a session id the student only ever held in memory, on the redirect after submit. Log out
   and the id is gone; the result page still exists and is still permitted, and nothing links to it.

**Fix:** advance `exam_registration.status` to `submitted` on submit, expose the session id on the
registrations list, and give the card a **Lihat hasil** action.

> **The new link must go through the same result gate as [issue #55](https://github.com/abak-academy/platform/issues/55).**
> `result_config = hidden` and `result_release_at` must be honoured on this path, or FB-27 ships a second
> bypass beside the one E3 is fixing. This is the single most important constraint on this item.
>
> **Correction — do not join the score into the list.** An earlier draft said to. `resultGate`
> ([`exam_result.go:115`](../../backend/internal/service/exam_result.go), used in five places) withholds
> the score in three states, so **a score field on the list response leaks exactly what the gate
> protects** — it would be a third bypass, not a fix. Expose only the session id and submitted-ness; let
> the result page apply the gate as it already does. Smaller change, and the correct one.

**Two submit paths, not one.** A student submit and an admin force-submit both end a session, so the
status transition belongs inside `SubmitSessionTx` — putting it in `SubmitSession` leaves every
admin-submitted registration stuck at `in_progress`.

**Spec position:** no FR names a student-facing history list, but **FR-COMP-27** says the certificate is
downloaded *"from the result page"* — which presumes the page is reachable. So **reachability is in
scope and the list itself is new** ([prd-trd-drift](prd-trd-drift.md) §2 item 14). FR-EXAM-16/17/18 are
all *admin* result-tab requirements — this is **not** FB-2.

**Two cross-references, both real:**

- The same status transition unblocks **FB-26**'s UI gate ([§8](#8-fb-26--multi-attempt-exams-approved-2026-07-30)) — so if
  multi-attempt is ever approved, this lands first.
- **FB-20/FB-33** (answer + position persistence, [E3](e3-exam-delivery-results.md) §4) touches the same
  session write path. Separable, but check for collisions if both are in flight.

## 6. FB-34 — the region seed is pre-2022 (34 provinces, not 38)

Exact and fixable. [`0029_seed_province_city_district.up.sql`](../../backend/db/migrations/0029_seed_province_city_district.up.sql)
is stamped:

```sql
-- Auto-generated from emsifa/api-wilayah-indonesia static data
-- Generated at: 2026-07-18T00:04:40+07:00
-- 34 provinces
```

**34 provinces, 514 cities, 7215 districts** — Permendagri 72/2019 vintage. Indonesia has had **38
provinces since 2022**; the file contains only `'91' PAPUA BARAT` and `'94' PAPUA`, so **Papua Selatan,
Papua Tengah, Papua Pegunungan and Papua Barat Daya are absent entirely**, along with the kabupaten
reassigned or created in that reorganisation. The *generation date* is recent; the *upstream dataset* is
not. A participant from those regions cannot complete their profile — exactly "belum lengkap".

**Do not truncate and reload.** `orders` FKs into all three tables
([`0033_shipping_ongkir.up.sql:5-9`](../../backend/db/migrations/0033_shipping_ongkir.up.sql)):

```sql
ALTER TABLE orders ADD COLUMN province_id TEXT REFERENCES province(id);
ALTER TABLE orders ADD COLUMN city_id     TEXT REFERENCES city(id);
ALTER TABLE orders ADD COLUMN district_id TEXT REFERENCES district(id);
```

A reload that reissues ids breaks every historical order's shipping address. Write it as an **additive**
migration against a current Kemendagri/BPS code list: insert the new provinces and kabupaten, re-parent
moved rows by id, leave existing ids alone. Ids here are official region codes, so a moved kabupaten
keeps its code and only its `province_id` changes — **that is the property that makes an additive
migration safe, and it must be verified against the source list before writing the migration.** If any
code was reissued, keep the old row and add the new one.

### Biteship is not the source of truth — checked 2026-07-30

**Answered, so this no longer gates the work.** Biteship is keyed on **postal codes**, not on our region
ids: [`biteship.go:109-110`](../../backend/internal/adapter/biteship.go) sends `origin_postal_code` (from
`app_kode_pos`) and `destination_postal_code`, and no shipping or adapter code reads `province`, `city`
or `district` at all. **We own this dataset outright** — there is no external list to defer to and no id
mapping to keep in sync, which is what makes an additive migration safe to write.

### The blast radius is wider than the reported symptom

The profile picker is only the surface the client happened to notice. Four consumers read these tables
([`repository/region.go`](../../backend/internal/repository/region.go)):

| Consumer | Effect of a missing region |
|---|---|
| Profile / address picker | The reported symptom — the student cannot complete their profile. |
| **`validateAddressHierarchy`** ([`store.go:604-628`](../../backend/internal/service/store.go)) | Validates province → city → district *"before it's persisted or used to price a shipment"*. **A student in an affected region cannot check out a physical order.** |
| **`student_bulk.go:213-255`** | Resolves regions **by name** for CSV import. A row naming a new province fails the import. |
| `orders.province_id / city_id / district_id` | Historical FK — the reason not to reload. |

So FB-34 blocks **checkout and bulk import**, not just a dropdown. That raises it above the P1 it was
filed as, and it is the strongest argument for doing it in this run rather than deferring it.

**Neither the PRD nor the TRD mentions province / city / district at all** — migration 0029 is entirely
unspecified shipped code ([prd-trd-drift](prd-trd-drift.md) §2 item 13). So there is no spec to conflict
with, and no spec to lean on either: the data source is an engineering decision.

## 8. FB-26 — multi-attempt exams (approved 2026-07-30)

*"6. Tidak bisa ujian lebih dari 1x padahal sudah di assign 2x attempt"* — **P0.**

**This item was blocked and is now answered.** The client wants exams retakeable, so the deferral is
reversed and the work is in scope. **Read the spec history below before implementing, because the code is
not wrong today — it is following a spec that is being changed.**

> **This reverses FR-COMP-02, a `Must`.** *"Every exam is single-attempt… `Exam.max_attempts` is stored
> but **not consulted** — multi-attempt/unlimited support **deferred**; remedial = a separate exam
> (superseded 2026-07-07)."* The TRD repeats it as a comment on both `max_attempts` and `attempts_used`.
> Sign-off recorded in [prd-trd-drift](prd-trd-drift.md) §1 entry 10.
>
> **Correction:** an earlier draft said those amendments must land "in the same PR as the code". **They
> cannot** — `requirements/` sits outside any git repository (`git rev-parse --show-toplevel` fails
> there), so the PRD and TRD are edited out-of-band. The **repo-side** record is
> `docs/backlog/prd-trd-drift.md`; that is what must change alongside the code, with the spec files
> amended separately.

**There are TWO attempt guards, not one.** The H1 analysis originally named only the SQL predicate. The
service layer refuses first, [`exam_session.go:366`](../../backend/internal/service/exam_session.go):

```go
if detail.AttemptsUsed >= 1 {
    return SessionStartPayload{}, ErrAlreadyAttempted
}
```

**Widening only the SQL leaves every retake blocked at this line**, with a different error. Both guards
have to move together, and the service-layer one must become a `max_attempts` comparison rather than
being deleted — it is what produces the friendly `ErrAlreadyAttempted` instead of a bare 409.

The guard is a hardcoded literal, [`exam.go:1349-1366`](../../backend/internal/repository/exam.go):

```sql
UPDATE exam_registration
SET attempts_used = attempts_used + 1, status = 'in_progress',
    checked_in_at = COALESCE(checked_in_at, now())
WHERE id = $1 AND attempts_used = 0      -- ← today's spec, becoming today's bug
```

`RowsAffected() == 0` → `ErrNoAttemptsLeft`. The `INSERT` in the same function has the same problem:
`attempt_number` is the literal `1`, so even with the predicate widened every attempt would claim to be
the first.

**Three parts, all inside the one transaction:**

1. `WHERE id = $1 AND attempts_used < $2`, passing `exam.max_attempts`. **Keep the check in the
   predicate** — moving it to the service layer reintroduces the race the original comment exists to
   guard against. That comment is the one piece of the old design to preserve.
2. `attempt_number` = `attempts_used + 1` from the returning row, not a literal.
3. **Define `max_attempts = 0` and `NULL`.** The column is nullable and the validator only rejects
   negatives ([`exam.go:649`](../../backend/internal/service/exam.go)), so today both mean "ignored".
   After this change they must mean something explicit — and every existing exam row has whatever is
   there now, so pick semantics that leave live exams single-attempt unless deliberately changed.

**Then the layer above — this is where it will look fixed and not be.** `computeCardState`
([`(student)/exam/page.tsx:70-71`](../../web/app/(student)/exam/page.tsx)) maps
`status === "in_progress"` to a detail link, not a Start action. **A registration stuck at
`in_progress` blocks the retry in the UI even after the SQL is correct** — and it is stuck because the
status never advances on submit, which is [§4](#4-fb-27--a-submitted-result-is-unreachable-after-logout)'s
fix. **FB-26 therefore depends on FB-27**, and both must be verified from the student's screen, not from
a passing repository test.

One open sub-question, and it is a real one: **a retake produces a second `exam_session` for the same
registration.** Which attempt does the result page show, which one does the certificate use, and which
one counts for the leaderboard? Highest score, or latest? Nothing in the code answers this today because
a second session was impossible. **Decide it before writing the query**, or the results surface will
quietly pick whichever row Postgres returns first.

## 9. FB-32 — audio is per question *and* per section (answered 2026-07-30)

*"12. Tidak muncul listening audio, padahal sudah di buat"* — **P0.**

**Answered: both scopes are supported.** The admin may attach audio to an individual question **or** to a
section test, and both must play. That resolves the PRD's self-contradiction in favour of the prose — see
[prd-trd-drift](prd-trd-drift.md) §1 entry 11.

**Both players already exist**; they share one over-tight gate
([`sessions/[id]/page.tsx:523,532`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx)):

```tsx
{isSectioned && activeTest?.section_type === "listening" && activeTest.audio_url && (…)}   // section
{isSectioned && activeTest?.section_type === "listening" && currentQ?.audio_url && (…)}    // question
```

`isSectioned` is true only for `mode = utbk | ielts`
([`isSectionedMode`, `exam.go:54`](../../backend/internal/service/exam.go)), so a `standard`-mode exam —
**the default** — renders neither.

**Fix:**

1. **Ungate the per-question player entirely.** It should render whenever `currentQ.audio_url` is set, in
   any mode and regardless of `section_type`. This is the whole bug the client reported.
2. **Keep the section player to sectioned exams, but drop the `section_type === "listening"` narrowing.**
   The admin sets `audio_url` on the test deliberately; requiring a second field to agree is the same
   inert-field trap as FB-26. In `standard` mode there are no sections, so section audio has no surface
   there — that is a limitation of the model, not a bug to fix.
3. **`audio_play_limit` does not exist for questions.** `test.audio_play_limit` shipped in migration
   0014; migration 0028 added only `question.audio_url`. The question player already passes no
   `playLimit`, so per-question clips are **replayable without limit** today.

> **Recommendation on the play limit: leave it unlimited, do not add the column.** Nobody asked for it and
> the simplest change closes the reported bug. **But flag it to the client** — for a real listening
> assessment, unlimited replay of a per-question clip may be precisely what they do not want, and that is
> a cheap follow-up migration (`question.audio_play_limit INT NULL`) once they have used it.

**Both players use `SectionAudioPlayer`** — the per-question one only differs by omitting `playLimit`. No
new component is needed.

**The PRD amendment is owed:** FR-EXAM-01 lists question attachments as *image only* and must gain audio;
FR-COMP-19a (section-level) stays as-is. Per FB-26's correction, `requirements/` is outside git so that
edit is out-of-band.

## 10. FB-31 — alt+tab is detected, counted, and then nothing happens — **CLOSED, no work**

> **ANSWERED 2026-07-30: keep the current behaviour — warn and log only, no consequence.**
> The client confirmed that detect + warn + log is what they want; no auto-submit, no forfeit, no
> review flag. FR-COMP-13 is therefore satisfied as shipped and **nothing is built for FB-31**.
> It is no longer a blocked item and should not be re-raised unless the client changes their mind.

The original analysis is kept below because it is what the decision was made on.

*"11. masih bisa di alt+tab & ada pemberitahuan pelanggaran"* — **not a defect, and not in this run.**

**The only item in the batch still waiting on the client.** Kept here rather than in a separate document
so all 15 items live in one place.

**FR-COMP-13 (Must) is fully satisfied**, which is why this is a feature request and not a repair:

> *"Proctoring events **detected, warned to student, and logged with timestamp**. Shipped vocabulary:
> `fullscreen_exit`, `tab_switch` (fires on any visibility change, which covers new-tab/new-window focus
> loss), `copy_attempt`."*

Detect, warn, log — three obligations, all three shipped. FR-COMP-12 likewise specifies only *"opens
fullscreen (Fullscreen API); re-prompted on exit"*, which is the overlay the client is seeing. **The spec
names no consequence**, so the system is behaving as designed: switching away is possible, it is
recorded, and it costs nothing.

[`sessions/[id]/page.tsx:265-291`](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx) listens on
`visibilitychange`, `fullscreenchange` and `copy`, posts to `/exam/sessions/:id/violations`, increments
`violationCountRef`, and shows an overlay. `violationCountRef` is then used in exactly one place —
**rendering the number** ([line 702](../../web/app/(exam-session)/exam/sessions/[id]/page.tsx)). No
threshold, no auto-submit, no server-side aggregate action. `LogViolation`
([`exam_session.go:787-820`](../../backend/internal/service/exam_session.go)) validates the type and
writes a row.

**What consequence do you want?**

| Option | Cost | Note |
|---|---|---|
| **Surface the count to the proctor live** | small | `GetRecentViolations` already feeds the monitoring view. Human judgement, no false-positive risk. **Recommended.** |
| Show it on the result / to the admin afterwards | small | Turns it into evidence rather than enforcement. |
| Auto-submit after N violations | small — the counter exists | Harsh: one accidental notification ends an exam. Needs an admin-settable N, **defaulting to off**. |
| Actually prevent alt+tab | **not possible in a browser** | No web API blocks it. Requires a lockdown browser or a native app. Say this plainly rather than promising a mitigation. |

Recommend proctor-visible **plus** an admin-configurable auto-submit threshold defaulting to off. **Do not
build any of it before the client picks** — this is the one item where the code is right and the *design*
is the open question.
